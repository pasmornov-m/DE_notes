# dbt (data build tool)

## Что такое dbt

**dbt (data build tool)** — это инструмент для управления SQL-трансформациями данных внутри аналитической базы данных или хранилища.

Он используется для преобразования **сырых (raw) данных** в **очищенные, согласованные и аналитически удобные таблицы**, которые затем используются BI-системами, отчётами или аналитикой.

Ключевая идея:

> dbt не загружает данные и не извлекает их — он управляет процессом их преобразования внутри базы данных.

---

## Где dbt используется в пайплайне данных

Типичный поток данных выглядит так:

```text
Источники данных
       ↓
  RAW таблицы
       ↓
      dbt
       ↓
 Аналитические таблицы (marts)
       ↓
 BI / отчёты / аналитика
```

dbt работает **после загрузки raw-данных** и **до аналитики**.

---

## Зачем нужен dbt

Сырые данные обычно:

* содержат ошибки и дубликаты
* имеют нестандартные имена колонок
* не соответствуют бизнес-логике
* требуют объединения с другими таблицами
* не подходят напрямую для аналитики

dbt решает задачи:

1. Очистки данных
2. Нормализации схем
3. Объединения таблиц
4. Добавления бизнес-логики
5. Создания аналитических витрин
6. Проверки качества данных
7. Управления зависимостями между преобразованиями

---

## Как работает dbt на практике

dbt использует SQL-файлы, которые называются **моделями (models)**.

Каждая модель — это SQL-запрос, который создаёт новую таблицу или view.

Пример staging-модели:

```sql
-- models/staging/stg_orders.sql

select
    id as order_id,
    cust_id as customer_id,
    amt as amount,
    ts as order_timestamp
from raw.orders
where status = 'completed'
```

После выполнения:

```bash
dbt run
```

будет создана новая таблица:

```text
stg_orders
```

---

## Многоуровневая архитектура моделей

dbt-проекты обычно строятся слоями.

```text
RAW → STAGING → INTERMEDIATE → MARTS
```

### 1. Staging слой

Назначение:

* очистка данных
* переименование колонок
* фильтрация невалидных записей
* приведение типов

Пример:

```sql
select
    cust_id as customer_id,
    email
from raw.customers
where email is not null
```

---

### 2. Intermediate слой

Назначение:

* объединение таблиц
* подготовка бизнес-логики

Пример:

```sql
select
    o.order_id,
    o.amount,
    c.customer_name
from {{ ref('stg_orders') }} o
join {{ ref('stg_customers') }} c
    on o.customer_id = c.customer_id
```

---

### 3. Mart слой

Назначение:

* создание аналитических таблиц
* агрегирование данных

Пример:

```sql
select
    date(order_timestamp) as order_date,
    sum(amount) as revenue
from {{ ref('int_orders_with_customers') }}
group by 1
```

Эти таблицы используются BI-системами.

---

## Управление зависимостями между моделями

dbt автоматически строит **граф зависимостей (DAG)**.

Пример:

```sql
from {{ ref('stg_orders') }}
```

Функция `ref()` означает:

* текущая модель зависит от `stg_orders`
* dbt сам определяет порядок выполнения

Это особенно важно при наличии десятков или сотен моделей.

---

## Встроенные тесты данных

dbt поддерживает автоматические проверки качества данных.

Пример:

```yaml
models:
  - name: customers
    columns:
      - name: customer_id
        tests:
          - not_null
          - unique
```

Можно запускать:

```bash
dbt test
```

Проверяются:

* NULL значения
* дубликаты
* нарушения ограничений

---

## Документация и lineage

dbt автоматически генерирует:

* граф зависимостей
* описание моделей
* происхождение данных (lineage)

Команды:

```bash
dbt docs generate
dbt docs serve
```

Это помогает понимать:

* откуда берутся данные
* какие таблицы зависят друг от друга

---

## Структура проекта dbt

Типичная структура:

```text
dbt_project.yml

models/
    staging/
    intermediate/
    marts/

tests/
macros/
seeds/
snapshots/
```

Основные элементы:

| Компонент | Назначение                |
| --------- | ------------------------- |
| models    | SQL-трансформации         |
| tests     | проверки данных           |
| macros    | повторно используемый SQL |
| seeds     | статические CSV           |
| snapshots | отслеживание изменений    |

---

## Отличие dbt от функций и процедур в БД

Важно понимать:
**dbt не заменяет SQL-функции, а решает другую задачу.**

### Stored procedures в БД

Используются для:

* выполнения SQL
* процедурной логики
* транзакций
* циклов и условий

Пример:

```sql
call build_daily_metrics();
```

Их может запускать планировщик, например по расписанию.

---

### Основное различие

```text
Stored procedures — выполняют SQL
dbt — управляет системой SQL-преобразований
```

---

## Сравнение dbt и функций в БД

| Критерий                 | Функции в БД          | dbt            |
| ------------------------ | --------------------- | -------------- |
| Управление зависимостями | вручную               | автоматически  |
| Архитектура              | часто монолитная      | модульная      |
| Тестирование данных      | вручную               | встроенное     |
| Документация             | вручную               | автоматическая |
| Lineage                  | сложно отслеживать    | встроен        |
| Повторяемость            | зависит от реализации | стандартная    |
| Версионирование          | сложно                | через Git      |

---

## Когда достаточно функций в БД

Использование функций оправдано, если:

* требуется процедурная логика
* используются транзакции
* есть циклы и условия
* небольшое количество таблиц
* нет сложной аналитики

---

## Когда имеет смысл использовать dbt

dbt становится полезным, если:

* много таблиц
* сложные зависимости
* большое количество SQL
* несколько разработчиков
* требуется контроль качества данных
* есть аналитические витрины

Особенно полезен при:

```text
50+ моделей
сложные JOIN
много бизнес-логики
```

---

## Взаимодействие с оркестраторами

dbt часто используется вместе с планировщиками задач.

Типичный пример:

```text
Raw загрузка → dbt → BI
        ↓
     Scheduler
```

Планировщик может запускать:

```bash
dbt run
dbt test
```

по расписанию или триггеру.

---

## Что создаёт dbt в базе данных

dbt создаёт:

* таблицы
* views
* materialized views

Он не хранит данные отдельно.

Пример итоговой схемы:

```text
raw.orders
raw.customers

stg_orders
stg_customers

int_orders

fact_orders
dim_customers
```

Все таблицы находятся в той же базе данных.

---

## Когда dbt может быть избыточен

dbt может быть не нужен, если:

* очень мало таблиц
* простые преобразования
* нет аналитических витрин
* логика редко меняется

---

## Итог

dbt — это инструмент для **структурированного управления SQL-преобразованиями данных**, который особенно полезен в аналитических системах с большим количеством таблиц и сложной бизнес-логикой.

Главное отличие от обычных SQL-функций:

```text
Функции выполняют отдельные операции.
dbt управляет всей системой преобразований данных.
```
